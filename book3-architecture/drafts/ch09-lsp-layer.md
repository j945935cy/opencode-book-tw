# 第 9 章　LSP 整合層

第二冊第 9 章從使用者角度講過 LSP 帶來的四種加成。這一章回答架構問題：語意能力是怎麼「接線」進代理迴圈的，以及如何從外部觀察它的健康狀態。

## 9.1 代理與語言伺服器的分工

先複習一個關鍵劃分：**LSP 是靜態的眼睛，測試是動態的裁判**。

LSP 負責不執行程式就能知道的事——型別錯誤、未定義符號、引用關係。它由 OpenCode 按設定自動啟動（偵測專案語言、拉起對應語言伺服器、等待索引完成），代理的編輯迴圈隨後消費其產出。

## 9.2 觀察點一：GET /lsp

伺服器把 LSP 狀態暴露為一等 API：

```bash
curl -s http://127.0.0.1:4096/lsp | python3 -m json.tool
```

回傳各語言伺服器的清單與狀態。除錯時的三種典型讀法：

- **不在清單** → 語言沒被識別或設定沒命中（回到第 8 章流程）
- **在清單但未就緒** → 大型專案索引中，等
- **就緒但代理仍拿不到診斷** → 問題在整合層，看日誌該伺服器的 stderr

## 9.3 診斷如何流進迴圈

一次編輯的生命週期裡，診斷的旅程是：

```text
edit 工具寫入檔案
   ↓ 語言伺服器收到檔案變更通知
重新分析 → 診斷集合更新
   ↓ OpenCode 收集
代理下一次決策時可見（錯誤是否已被自己修好）
```

這解釋了第二冊的一個現象：「代理改完碼會自己看一眼有沒有改對」。不是魔術——是編輯後的診斷查詢成為迴圈的一部分。也解釋了為什麼 LSP 未就緒時代理品質會明顯下滑：眼睛還沒睜開。

## 9.4 formatter 子系統

官方文件將 formatter 列為獨立配置項，並提供 `GET /formatter` 端點觀察狀態。設計上 formatter 與 LSP 平行：前者管格式（存檔時套用 prettier/gofmt 等），後管語意。兩者都遵循同一模式——**外部程序、生命週期託管、狀態可查詢**。

這個模式的價值在於一致性：你學會用 `/lsp` 除錯，就會用 `/formatter`；反之亦然。

## 本章摘要 {.unnumbered .unlisted}

- 分工鐵律：LSP 管靜態、測試管動態。
- `/lsp` 端點三種讀法：缺席→設定問題、未就緒→索引中、就緒無效→看日誌。
- 「改完自查」的本體是編輯後診斷查詢。
- LSP 與 formatter 共享「外部程序＋狀態可查」模式。
