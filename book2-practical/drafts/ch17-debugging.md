# 第 17 章：除錯與問題修復

除錯最能看出代理使用的功力差距：同一個 Bug，有人三個回合定位根因，有人讓 AI 改了八輪越改越歪。差別不在模型，在於有沒有讓它走科學方法。這章給出系統化除錯的提問框架，以及日誌分析的實戰手法。

## 17.1 系統化除錯提問法

**先禁止開藥**

除錯最大的反模式是第一句話就要求「修好它」。正確的第一步是**把診斷與治療分離**：

```text
這個 Bug 的現象如下……
請先只做診斷：
1. 列出三個最可能的假設
2. 為每個假設設計一個最小驗證實驗（跑什麼指令、看什麼結果）
3. 按成本由低到高排序執行
找到根因後停下來回報，等我確認再動手。
```

「三個假設」是關鍵設計——強迫模型提出多個候選解釋，避免它在第一個看似合理的解釋上鑽牛角尖。「按成本排序」則把你的時間花在刀口上。

**根因確認的黃金標準**

一個合格的根因必須滿足：能完整解釋所有症狀、能用實驗重現、修掉之後症狀消失且沒有新症狀。三者缺一，都只是「碰巧有效」的偏方。AI 回報根因時，用這三條檢驗它。

**症狀資訊的最小完備集**

提供線索時，這五項給齊就夠 AI 開工：

| 項目 | 範例 |
|------|------|
| 預期行為 | 送出表單應建立訂單並跳轉 |
| 實際行為 | 無回應，console 顯示 500 |
| 重現步驟 | 填寫含特殊字元的地址後送出 |
| 環境 | 本地 docker compose，昨天還正常 |
| 已知變化 | 昨天合併了地址格式化的 PR |

最後一項「已知變化」經常被漏掉，卻往往是破案最快的線索——大多數 Bug 來自最近的變更。

**防瞎槍條款**

AI 在兩次修正失敗後容易進入亂槍打鳥模式（隨機加 try-except、無依據地改設定）。提前立規矩：

```text
若連續兩次修正未解決，停止修改，
回到假設列表重新評估，告訴我你排除了什麼、還剩什麼可能。
```

## 17.2 日誌分析與錯誤追蹤

**把 log 直接餵對話**

終端機輸出的錯誤訊息直接複製貼上（比截圖更好——文字可被精確引用）。長日誌存成檔案再請代理讀：

```bash
docker compose logs api > /tmp/api.log
```

```text
/tmp/api.log 是服務崩潰前五分鐘的完整日誌。
找出第一個異常點與後續症狀的因果順序。
注意區分「原因」和「連帶反應」——堆疊尾端的錯誤常常只是受害者。
```

那段提醒很值錢：新手讀 log 最常犯的錯就是盯著最後一行（通常是連帶效應）當元兇。

**跨服務追蹤**

微服務架構的問題要靠 request ID 串場：

```text
這是同一個請求在三個服務的日誌摘錄。
用 trace-id 對齊時間軸，指出延遲發生在哪一跳、
失敗從哪個服務開始傳播。
```

**log 不夠時：加觀測而不是加猜測**

診斷卡住的正確下一步是增加可觀測性，不是加大膽猜測：

```text
我們無法確認佇列消費者是否收到訊息。
請在消費者入口加上結構化日誌（含 message id 與時間戳），
部署到本地環境後幫我重跑重現流程並收集證據。
```

先補儀器、再收集資料、再下結論——科學方法的順序在除錯中一字不改。

## 本章摘要 {.unnumbered .unlisted}

- 診斷與治療分離；「三個假設＋最小驗證實驗＋成本排序」是除錯提問的骨架。
- 根因三檢：解釋全部症狀、實驗可重現、修後無副作用。
- 症狀五件套：預期、實際、重現步驟、環境、最近變更；「已知變化」常是最短破案路徑。
- 兩次修正失敗就強制回到假設評估，杜絕亂槍打鳥；log 分析注意首因與連帶之別；資訊不足時先加觀測再加判斷。
