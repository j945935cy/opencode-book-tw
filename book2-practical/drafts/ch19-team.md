# 第 19 章：團隊協作

前面十八章練的都是個人武功；這章處理放大問題——怎麼讓整個團隊的 OpenCode 用出一致的水準，以及在敏感環境裡怎麼守住資料的門。核心原則只有一句話：**能版控的都版控，不能外流的都不外流。**

## 19.1 共用設定與技能的版控策略

**三層資產，三種命運**

| 資產 | 位置 | 版控策略 |
|------|------|----------|
| 團隊規範與技能 | `.opencode/`（opencode.json、skill/、command/、agent/） | 進儲存庫，跟著 code review |
| 個人偏好 | `~/.config/opencode/` | 不進版控，各自為政 |
| 敏感憑證 | auth.json、環境變數 | 永遠不進任何儲存庫 |

判斷標準很簡單：這個設定換一個人來用還成立嗎？成立就放專案層共享（第 12 章的合併機制保證個人層可以再客製），只對某個人才成立的就留全域。

**AGENTS.md 的治理**

第 7 章把 AGENTS.md 定位成「給 AI 的團隊簡報」，團隊場景下要多兩條治理規則：

- **變更走 PR**。改 AGENTS.md 等於改所有人的 AI 行為，必須可審查可追溯。
- **指定維護者**。文件沒有 owner 就會腐爛。每季一次巡檢：過時的指令刪掉、AI 反覆犯錯的新規則補上。

**技能庫的團隊經營**

把第 5 章的技能機制升級為團隊知識工程：

1. **收編口耳相傳**。新人問第三次以上的流程，寫成技能。
2. **命名空間紀律**。技能名稱用「領域-動作」格式（如 deploy-checklist、db-migration），避免撞名與語義模糊。
3. **定期演練**。季度挑兩支關鍵技能實測觸發與效果，過時描述及時更新。

**新成員 onboarding 清單**

- 安裝 OpenCode 並釘到團隊基準版本（第 6 章）
- clone 儲存庫——AGENTS.md 與 `.opencode/` 自動到位
- 全域設定只需放個人偏好
- 第一個任務：請代理帶著讀一遍 AGENTS.md 並總結團隊慣例

## 19.2 敏感專案的分享政策

**分享功能的全域停用**

`/share` 把會話發布成公開網址（第 11 章），在受監管或競爭敏感的環境裡必須封死：

```json
{
  "share": "disabled"
}
```

寫在專案層 `.opencode/opencode.json`，整個儲存庫的協作者一律無法分享。組織若有多個敏感專案，也可以放在全域層按需在個別非敏感專案開啟。

**本地模型：資料不出門的底線方案**

當程式碼依法不得離開內網（金融、醫療、國防場景），雲端模型 API 就不是選項。OpenCode 支援接 Ollama、vLLM 等本地推論端點：

```json
{
  "provider": {
    "ollama": {
      "npm": "@ai-sdk/openai-compatible",
      "options": { "baseURL": "http://内网推理机:11434/v1" }
    }
  }
}
```

代價是模型能力上限取決於內網硬體，複雜任務的品質會打折。務實的做法是分級：公開元件用雲端旗艦模型，敏感模組切本地模型——`--model` 參數與代理層模型覆寫（第 20 章）讓分級操作成本趨近於零。

**憑證衛生**

- 供應商金鑰放環境變數或 auth.json，絕不出現在會話內容與日誌中。
- MCP 伺服器的 token 按「最小必要範圍」申請（第 10 章）。
- 離職交接清單記得包含：撤銷該成員的 GitHub 整合授權與各供應商金鑰。

## 本章摘要 {.unnumbered .unlisted}

- 三層資產三種命運：團隊規範進版控、個人偏好留全域、憑證永不入庫。
- AGENTS.md 與技能庫要有治理：PR 變更、指定維護者、季度演練。
- 敏感專案以 `"share": "disabled"` 封鎖對話外流；法規級需求走本地模型端點，能力分級取捨。
- 憑證最小化與離職撤銷是長期安全的基本功。
