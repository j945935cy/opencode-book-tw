# 第 6 章　工具執行迴圈內幕

工具是代理的手腳。這一章解剖一次工具呼叫從誕生到收尾的全過程，以及兩個最容易被忽略的設計：權限閘門的位置與大型輸出的去路。

## 6.1 工具呼叫的誕生

模型輸出「我想執行 bash 指令 X」時，這個意圖先落成一個 `part`——type 標記為工具呼叫、data 帶著指令內容與狀態。注意順序：**先持久化，後執行**。

這個順序是刻意的安全設計：即使進程當場崩潰，「代理曾經想幹嘛」已經留了案底。事後審查任何一次事故，都能從 parts 鏈完整重放決策路徑。

## 6.2 權限閘門的位置

第二冊把 permission 規則講成使用者的視角（allow/ask/deny）；架構視角要問的是：閘門卡在哪？

答案：**卡在「意圖 part 已落盤」之後、「實際執行」之前**。規則比對以工具類別為第一層（edit、bash、webfetch、mcp），bash 再細分到指令前綴——`git push*` 與 `git status` 可以天差地遠。

當規則判定為 `ask`，迴圈在此暫停：請求寫入 DB 的 permission 相關記錄，同時透過事件流廣播給客戶端；客戶端彈出確認框；你的點擊經由 `/session/:id/permissions/:permissionID` 端點回填。等待期間伺服器與會話狀態保持一致——斷線重連也不會讓「待批准」憑空消失。

## 6.3 大型輸出的去路

跑一輪測試套件，輸出動輒數萬行。全塞進資料庫？`tool-output/` 目錄就是解法：

```text
~/.local/share/opencode/tool-output/tool_00b81a239001...
```

每個 `tool_*` 檔對應一次大型工具結果。資料庫裡的 part 只存中繼資料與指標；需要完整輸出時按名取檔。實測此機制的兩個好處：

1. **DB 瘦身**：398MB 的庫裡若塞滿建置日誌，查詢與備份都成災。
2. **串流友好**：part 先帶著「摘要＋指標」即時上屏，全文按需讀取。

## 6.4 失敗、中止與痕跡

三種非正常結束各有資料特徵：

- **工具失敗**：結果 part 帶錯誤標記回填——模型看得到失敗詳情，於是有了自我修復的原材料。
- **使用者中止**（Esc）：回合停在當前 part，已完成的部分保留。沒有任何東西被悄悄抹掉。
- **revert 回退**：不是刪除而是標記（session.revert），可 unrevert 反悔。

「一切皆痕跡」是這個系統除錯體驗好的根本原因。

## 本章摘要 {.unnumbered .unlisted}

- 工具意圖先落盤再執行——崩潰也留有案底。
- 權限閘門位於落盤之後、執行之前；ask 透過 API 端點回填。
- 大型輸出溢寫 tool-output 目錄，DB 只留指標。
- 失敗、中止、回退全部以標記而非刪除處理。
