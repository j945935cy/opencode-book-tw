# 第 11 章　本地 git 流：pr 命令與提交紀律

平台自動化是「代理去找活」；本章講「你把活帶給代理」。`opencode pr <number>` 一行命令把 GitHub PR 檢出到本地分支並直接啟動會話——審查、接手、修復一氣呵成。順帶把第二冊的 commit 紀律升級成團隊版。

## 11.1 pr 命令：一行進入戰場

```bash
opencode pr 1234
```

它做三件事〔實測 --help 描述〕：抓取編號 1234 的 PR 分支、checkout 到本地、然後**直接在該分支上啟動 opencode 會話**。傳統流程（gh pr checkout 1234 && opencode）被壓縮成一行。

適用場景：

- **審查前先體驗**：看 diff 不如跑起來。檢出後讓代理幫你跑測試、解釋改動意圖
- **接手他人的半成品**：同事請假的 WIP PR，代理讀完變更後告訴你還缺什麼
- **修復審查意見**：在 PR 分支上叫代理照 review comments 批量修改

前提只是 gh 可用且已登入——命令底層走 GitHub CLI 的認證〔文件〕。

## 11.2 審查工作流：代理當副駕

把 pr 命令嵌進日常審查循環：

1. 收到 review 請求，`opencode pr <n>` 檢出
2. 讓代理跑一遍：`這個 PR 改了什麼？有沒有遺漏的邊界情況？`
3. 自己讀關鍵檔案，形成判斷
4. 回到 GitHub 留下審查意見；需要小修的地方直接說 `/oc` 讓平台側代理處理（第 7 章）

人的注意力花在判斷，代理的算力花在掃描——分工清楚，審查品質與速度同時提升。

## 11.3 團隊版 commit 紀律

第二冊教過原子提交與訊息規範；多人加代理之後，倉庫裡多了一種新作者。紀律補丁三條：

**補丁一：代理產出的 commit 要標記來源。** 平台整合天然帶身分（GitHub App 或 GitLab service account）；本地會話裡讓代理提交時，訊息加上約定前綴（如 `ai:`），追溯成本趨近於零。

**補丁二：大變更必須過 PR。** 本地會話再順手，直推 main 的誘惑也要擋住——PR 流程是審查自動化（第 8 章 pull_request 事件）的前提。

**補丁三：revert 靠快照也靠 git。** 第三冊講的 revert 是會話內的時間旅行；已經 push 出去的歷史，還是要靠 git 本身的機制收拾。兩層安全網各管一段。

## 11.4 分支策略與代理的配合

| 分支模型 | 代理用法 |
|----------|----------|
| feature branch | 每個功能分支配一個會話；pr 命令檢出他人分支接力 |
| trunk-based | 短命會話＋高頻小 PR；pull_request 自動初審價值最大化 |
| release branch | 排程巡檢（第 9 章配方三）盯 cherry-pick 遺漏 |

無論哪種模型，原則相同：代理的寫入一律經過 PR 閘門，分支保護規則對 AI 作者與人類作者一視同仁。

## 11.5 本章摘要

- `opencode pr <n>`＝抓取＋checkout＋啟動會話，一行完成審查前置
- 審查分工：代理掃描、人類判斷、平台代理收尾
- 三補丁：來源標記、大變更必過 PR、會話 revert 與 git revert 各管一段
- 分支模型不拘，寫入必經閘門的原則不變
