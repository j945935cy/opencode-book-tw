# 第 11 章　插件系統

插件是第三種擴充軸：MCP 加工具、skills 加知識、插件加行為。這一章從資料目錄的實際痕跡反推插件的運作方式與安全邊界。

## 11.1 眼見為憑：storage 目錄

真實機器的 `~/.local/share/opencode/storage/`：

```text
agent-usage-reminder/
oh-my-openagent/
```

兩個目錄對應兩個實際存在的擴充。`oh-my-openagent` 來自本機設定檔的 plugin 區塊（帶 @latest 版本標記）；`agent-usage-reminder` 則是某個已安裝擴充留下的資料目錄。這告訴我們兩件事：

1. 插件以 npm 套件形式分發（名稱＋版本範圍）
2. 插件可以在 storage 下擁有自己的持久化空間

## 11.2 插件能做什麼

官方文件〈Plugins〉定義的模型：插件是載入進核心的程式碼，透過**鉤子**參與系統事件——例如在工具執行前後插入邏輯、觀察會話事件、修改行為細節。

與 MCP 的本質區別：

| | MCP | 插件 |
|--|-----|------|
| 形態 | 獨立進程/端點 | 核心內載入 |
| 能力 | 只提供工具 | 攔截與改變行為 |
| 故障半徑 | 隔離（掛了不影響核心） | 共生（寫壞會拖垮主程序） |
| 權限 | 受 permission 規則管 | 完全信任 |

## 11.3 安全邊界的真相

上一張表的最後一行值得放大：**安裝插件＝把完全信任交給一個第三方套件**。它不在沙盒裡、不受 permission 閘門管束，因為它就是「閘門的一部分」。

務實守則：

- 只裝審過原始碼或來源可信的插件
- 鎖版本（避免 @latest 自動吃到供應鏈攻擊的新版）
- 企業環境優先考慮 MCP 路線達成同樣需求

第二冊第 21 章說「deny 清單優先」是使用者的安全基線；這一章補上開發者的那條：**擴充需求先問能不能用 MCP，再考慮插件**。

## 本章摘要 {.unnumbered .unlisted}

- 三條擴充軸：MCP 加工具、skills 加知識、插件加行為。
- 插件以 npm 套件分發，可在 storage 持久化資料。
- 鉤子模型讓插件攔截並改變行為——代價是完全信任。
- 選型順序：先 MCP 後插件；裝插件必鎖版本。
