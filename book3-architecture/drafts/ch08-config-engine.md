# 第 8 章　設定解析引擎

第二冊第 12 章教你「七層優先序」排查設定問題；這一章下到引擎室，看合併本身怎麼發生、以及兩個官方 API 如何讓設定變成可觀察的對象。

## 8.1 七層合併語意

由高到低回顧（細節見第二冊）：

```text
CLI 旗標 → 代理定義 → 額外指定檔 → 專案層 → XDG 使用者層 → 全域層 → 內建預設
```

引擎室視角補三個關鍵語意：

**深合併而非覆蓋。** 物件型欄位（如 mcp、permission）逐鍵合併：專案層只寫一個 MCP 伺服器，不會清掉全域層定義的其他伺服器。陣列型欄位則多為整體取代——混用時要小心。

**載入順序可觀察。** 日誌裡明確記錄每個被載入的設定檔路徑（`message=loading path=...`）。設定沒生效時，先看日誌確認「它到底讀了哪些檔」，再談合併對錯。

**JSONC 全程支援。** 所有設定檔允許註解與尾逗號——配置即文件。

## 8.2 $schema 與編輯期防呆

真實機器的設定檔開頭：

```json
{
  "$schema": "https://opencode.ai/config.json",
  ...
}
```

掛上 schema 後，編輯器能在你打錯欄位名當下畫紅線——比執行期除錯便宜一個數量級。schema 本身也是文件：所有合法欄位、型別、預設值一目了然。

## 8.3 把設定變成 API 對象

架構上漂亮的一點：設定不是黑盒，而是伺服器的一等公民：

- `GET /config`：取回當前生效的合併結果
- `PATCH /config`：程式化修改設定
- `GET /config/providers`：供應商與預設模型的生效視圖

實用場景：懷疑專案層某條規則蓋掉了全域，直接 GET 合併結果搜關鍵字，五秒定案——不用再腦內模擬七層疊加。

## 8.4 除錯流程模板

遇到「改了沒效」的標準五步：

```text
1. 日誌：確認檔案有被載入（loading path=...）
2. JSON 語法：註解/尾逗號是否破壞了檔案
3. GET /config：確認合併結果含目標值
4. 若無 → 逐層二分：暫時搬移設定到更高層測試
5. 若有 → 問題在消費端（重啟？該功能讀的是別的鍵？）
```

## 本章摘要 {.unnumbered .unlisted}

- 深合併逐鍵疊加、陣列整體取代；日誌記錄每次載入。
- $schema 提供編輯期驗證與自帶文件。
- 設定是 API 一等公民：GET 觀察、PATCH 修改。
- 五步除錯模板把玄學變成流程。
