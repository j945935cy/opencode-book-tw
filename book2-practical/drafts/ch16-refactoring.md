# 第 16 章：程式碼重構

重構是「改好程式而不改變行為」，聽起來單純，實作上卻是 AI 代理最容易出事的場景——因為它需要同時維持兩件事：對現有行為的精確理解，以及大範圍修改的一致性。這章談兩件事：怎麼選重構策略，以及怎麼搭安全網讓任何重構都死不了人。

## 16.1 重構策略選擇

先分清楚你要的是哪一種重構，策略完全不同：

| 類型 | 範例 | 風險 | 策略 |
|------|------|------|------|
| 機械式重構 | 改名、搬檔案、抽函式 | 低 | 可大幅委託 AI，LSP 把關 |
| 結構性重構 | 分層調整、拆模組、換設計模式 | 中 | 計畫審核＋分段執行 |
| 行為邊界重構 | 換資料格式、改介面契約 | 高 | 測試補強後才准動工 |

**機械式重構：放心交出去**

改名與搬移有 LSP 引用查找護航（第 9 章），AI 做這類工作又快又穩：

```text
把 OrderService.rename 後面的整條呼叫鏈整理乾淨：
所有命名不一致的私有方法統一改成動詞開頭，
用 LSP 引用查找確認每處更新到位，最後跑測試。
```

**結構性重構：拆成遷移序列**

「把散落各處的驗證邏輯收進 Validator 層」這種任務，關鍵動作是請代理把它拆成一串可獨立驗收的小遷移，而不是一次大爆炸：

```text
目標：將三個 handler 內的訂單驗證邏輯收斂到 internal/validator/。
要求產出遷移序列：每一步只搬一個 handler，
搬完跑全量測試並 commit。
中途不得順手改任何行為語意——這次是純搬家。
```

那句「純搬家」很重要。重構與功能修改混在同一批變更裡，是 code review 的災難；分成兩個 PR 才是人道的。

**行為邊界重構：先補測試再動手**

要動介面契約之前，現有行為必須被測試釘住。流程永遠是：請代理依現狀寫特徵測試（characterization test）→ 全綠 → 才允許開始重構 → 全程測試不得轉紅。跳過第一步的行為邊界重構，等於蒙眼走鋼索。

## 16.2 安全重構：測試先行＋git 快照

安全網由兩層組成，缺一不可。

**第一層：git 快照**

重構開始前確保工作區乾淨（已 commit 或 stash）。之後的紀律是第 15 章講過的小步提交——每一小步都是一個可以回頭的路標：

```bash
git checkout -b refactor/order-validator
# ...一小步...
git commit -m "refactor: 搬移 createOrder 驗證至 validator"
# ...又一步...
git commit -m "refactor: 搬移 cancelOrder 驗證至 validator"
```

出事時 `git bisect` 配合測試指令能自動定位第一個轉紅的提交；就算不用 bisect，回退粒度也在「一步」而不是「整個重構」。

**第二層：測試當裁判**

重構期間的測試規則只有一句話：**測試程式本身凍結**。你測的是「行為不變」，如果重構過程順手改了測試，裁判就下場打球了。

代理若提出「順便把這個過時的測試也修一下」，標準回應是：「記下來，重構完成後另開任務處理。」

**失敗案例解剖**

一次典型的翻車迴路值得記住：AI 重構中測試轉紅 → 它判斷「這個測試寫得太綁細節」→ 修改測試讓它變綠 → 實際上它已經悄悄改變了行為。防禦方法就是把上述規則明說：

```text
重構全程 tests/ 目錄禁止修改。
任何測試失敗都視為你的修改引入了行為變化，
請修正你的程式碼而不是測試。
```

## 本章摘要 {.unnumbered .unlisted}

- 三種重構風險梯度：機械式（放心委託）、結構性（拆遷移序列）、行為邊界（先補特徵測試）。
- 重構與功能修改分流成不同 PR；「純搬家」要在指令裡明示。
- 安全網雙層：git 小步快照提供回退路標，凍結的測試套件擔任行為裁判。
- 最危險的陷阱是代理修改測試來「通過」——把禁令寫進提示詞或 AGENTS.md。
