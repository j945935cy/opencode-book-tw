# 第 7 章：理解程式碼

> **本章學習目標**
>
> - 用三段式問法快速搞懂一段陌生程式碼
> - 讓代理替你畫出專案的地圖
> - 產生可直接使用的說明文件與註解
>
> **預估閱讀時間**：12 分鐘
> **實作時間**：約 15 分鐘（建議拿真實專案練習）

---

「讀懂別人的程式碼」佔工程師日常時間的比例，遠高於多數人的想像。這正是代理最擅長、也最安全的工作——**閱讀不產生任何變更風險**。本章三個情境，全部建議在 Plan 模式下進行。

## 7.1 問懂一段程式碼

拿到一份看不懂的檔案，用三段式問法：

```text
@src/services/export.ts
1. 這個檔案的職責是什麼？
2. exportRecords() 函式的執行流程，逐步說明
3. 有哪些邊界情況沒有被處理？
```

為什麼拆成三問而不是一句「解釋這個檔案」？

- 第一問要的是定位（它負責什麼）
- 第二問要的是流程（怎麼運作）
- 第三問要的是洞見（哪裡有坑）

一次全要，回答容易變成流水帳；分層追問，每一層都能繼續深挖。例如第三問的答案提到「未處理磁碟空間不足」，你可以立刻追：「如果匯出到一半磁碟滿了，使用者會看到什麼？」

### 追問鏈的威力

代理回答後的追問，比初始提問更有價值：

```text
第 42 行為什麼要用 setTimeout 而不是直接呼叫？
```

```text
如果把這個 callback 改成 async/await 會影響哪些呼叫端？
```

這種「針對具體行號與決策點」的追問，往往能挖出連原作者都答不上來的歷史包袱。

## 7.2 摸清專案架構

接手新專案的第一小時，與其自己亂逛，不如讓代理當嚮導。依序問這四題：

```text
1. 這個專案用了哪些主要技術？版本呢？
2. 從使用者發一個請求到資料寫入資料庫，中間經過哪些層？
3. @src/ 底下的資料夾各自負責什麼？
4. 有沒有看起來沒人用、可能是遺留物的程式碼？
```

第四題要小心對待——代理指出的「疑似死碼」需要驗證（全域搜尋引用、查 git 歷史）才能下結論，但作為線索來源極有價值。

把答案整理成你自己的筆記。也可以反過來讓代理輸出：

```text
把剛才的討論整理成 ARCHITECTURE.md 大綱，放在 Plan 回覆裡給我。
```

## 7.3 產生說明文件

文件是代理的舒適圈，但品質取決於你的要求方式。

### 為函式補 docstring／註解

```text
@src/utils/date.ts
為這個檔案裡所有 exported 的函式補上 JSDoc 風格註解，
包含參數型別、回傳值，以及至少一個使用範例。
不要更動任何程式邏輯。
```

注意結尾那句「不要更動任何程式邏輯」——明確圈出行為邊界，是文件類任務的安全帶。

### 為專案補 README 章節

```text
根據這個專案的實際狀況，幫 README.md 補上「開發環境建置」
與「常見問題」兩個章節。建置指令以 AGENTS.md 為準，
常見問題請從最近三十天的 commit 訊息與 issue 標題推測。
```

這個提示詞示範了兩件事：指定事實來源（AGENTS.md）、指定推理素材（commit 與 issue）。代理產生的文件因此貼近現實而非憑空編造。

> **注意**：AI 生成的文件初稿必須人工校訂後再提交，尤其是「版本號、路徑、指令」這類硬事實。文件錯了比沒有文件更糟。

## 本章摘要 {.unnumbered .unlisted}

- 讀碼三段式：職責定位 → 流程拆解 → 邊界情況；分層追問優於一次全要。
- 架構四問：技術棧、請求旅程、資料夾職責、疑似遺留物。
- 文件任務務必圈定行為邏輯（「不要動程式碼」）、指定事實來源，產出後仍需人工校訂。
- 本章所有情境都在唯讀範圍內，是練習代理互動零風險的沙盒。
