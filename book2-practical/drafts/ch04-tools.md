# 第 4 章：工具系統

如果代理是大腦，工具就是手腳。模型再聰明，沒有工具就只是個聊天機器人。OpenCode 的內建工具家族經過刻意收斂——數量不多，但每一件都足夠強，而且彼此的分工界線畫得很清楚。這一章帶你盤點這套「手腳」，並深入兩個值得理解的設計細節：編輯工具的多層回退比對，以及不同模型能力差異如何被架構吸收。

## 4.1 內建工具分類

內建工具按用途分成五類：

| 類別 | 代表工具 | 用途 | 權限屬性 |
|------|----------|------|----------|
| 讀取 | read、glob、grep | 看檔案內容、按名稱找檔案、按內容搜尋 | 唯讀，通常放行 |
| 寫入 | edit、write | 精準修改既有檔案／整檔建立覆寫 | 受 `permission.edit` 管控 |
| 執行 | bash | 跑 shell 指令：測試、建置、git、安裝 | 受 `permission.bash` 管控 |
| 網路 | webfetch | 抓取指定 URL 轉成文字供分析 | 受 `permission.webfetch` 管控 |
| 委託 | task | 把子任務交給其他代理（第 3 章） | 隨被委託代理的權限 |

三個容易誤解的地方：

**grep 和 glob 是兩種搜尋。** glob 按「檔名模式」找路徑（例如 `src/**/*.ts` 找出所有 TypeScript 檔），grep 按「內容正規表示式」找位置（例如找出所有呼叫 `connectToServer` 的行）。AI 會自己選對的工具，但你看懂輸出時知道差別會很有幫助。

**bash 是權限焦點。** 五類工具中只有 bash 能觸發任意副作用（刪檔案、推程式碼、裝套件），所以第 3 章的權限範例幾乎都圍繞它設計。

**read 不是拿來取代 grep 的。** 大檔案直接整讀既浪費上下文又慢；正確姿勢是先用 grep 定位行號，再針對性讀取區段。好代理會這麼做，你驗收時也可以看它是不是這麼做。

## 4.2 Edit 工具的多層回退比對

edit 工具的運作方式是「提供舊字串與新字串，把舊字串換成新字串」。理論上簡單，實務上有個麻煩：模型的複製貼上偶爾不完美——縮排差一格、引號形式不一致、行尾空白多一個。嚴格逐字元比對的話，大量本可成功的編輯會無謂失敗。

OpenCode 的解法是**多層回退比對**（fallback matching）：先嘗試最嚴格的精確比對，失敗後依序放寬條件重試：

```text
第一層：精確匹配（逐字元）
   失敗 ↓
第二層：忽略縮排差異（相對縮排不變即視為相同）
   失敗 ↓
第三層：忽略跳脫序列差異（如 \n、引號形式）
   失敗 ↓
回報失敗，請模型重新確認內容
```

這個設計的意義在**成功率與安全性的平衡**：放寬的是「無關緊要的格式差異」，不放寬的是「語意內容」——任何一層的替換仍然必須唯一命中目標區塊，不會因為模糊比對改錯地方。

對你的實際影響只有一件事：**審查 diff 的習慣不能省**。回退機制讓編輯更常成功，但「成功」永遠指「照新字串改了某處」，改得對不對仍要靠你在 TUI 的 diff 檢視裡過目。第 16 章的重構工作流會把這件事變成流程的一部分。

## 4.3 工具與模型能力的適配

各家模型的「手感」不同。以 OpenAI GPT 系為例，它在自家生態慣用 apply_patch 形式的補丁編輯；Anthropic Claude 系則習慣整段替換式的 edit。若要求每個使用者自己研究「哪家模型該配哪種編輯模式」，體驗就完了。

OpenCode 的處理方式是**供應商適配層**：統一的內部工具協定之下，依模型自動調整實際下達的編輯指令形態。你切換模型時（快速鍵或 `--model` 參數），工具系統跟著換檔，但介面、權限、會話紀錄全部不變。

這個抽象還有一個附帶好處：日誌裡看到的工具事件是標準化的。排查「AI 為什麼改壞檔案」時，你讀到的事件序列在任何模型下長得一樣，不必先學一遍各家的原始格式。翻查日誌的方法見第 22 章。

## 本章摘要 {.unnumbered .unlisted}

- 內建工具五分類：讀取（read／glob／grep）、寫入（edit／write）、執行（bash）、網路（webfetch）、委託（task）；bash 是唯一的任意副作用入口，也是權限設計的重心。
- glob 找檔名、grep 找內容；先定位再讀取是省上下文的正確姿勢。
- edit 採多層回退比對：精確→忽略縮排→忽略跳脫，提升成功率但不犧牲唯一命中；diff 審查仍是你的責任。
- 供應商適配層吸收模型間的編輯風格差異（如 GPT 系的 apply_patch），切模型不必改習慣。
