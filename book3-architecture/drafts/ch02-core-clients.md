# 第 2 章　一個核心、多種面孔

用過 OpenCode 幾天之後，你可能注意到一件怪事：IDE 外掛裡出現的會話，終端機裡也看得到；`opencode serve` 起的伺服器，瀏覽器也能操作同一批會話。這不是同步功能的功勞——而是因為它們本來就長在同一個核心上。

## 2.1 官方說法：TUI 只是客戶端

官方文件〈Server〉頁有一句關鍵描述：

> 當你執行 `opencode` 時，它同時啟動了一個 TUI 和一個伺服器。TUI 是與伺服器對話的客戶端。

這句話是全書最重要的架構事實。你每天盯著看的終端機介面，並不是 OpenCode 的「本體」——它只是一個畫得漂亮的遙控器。真正的核心（會話管理、工具執行、權限判斷、資料持久化）全部住在伺服器進程裡。

**驗證方法**：啟動 TUI 後另開一個終端機，查詢隨機指派的埠（或用 `--port` 固定），對健康檢查端點發請求：

```bash
opencode serve --port 4096 &
curl http://127.0.0.1:4096/global/health
# {"healthy":true,"version":"..."}
```

## 2.2 客戶端家族

同一個伺服器核心，至少對應四種官方客戶端形態：

| 客戶端 | 形態 | 適合場景 |
|--------|------|----------|
| TUI | 終端機互動 | 日常開發主力 |
| Web | 瀏覽器介面（opencode web） | 遠端主機、手邊只有平板 |
| IDE 外掛 | 編輯器內嵌面板 | 邊寫碼邊呼叫代理 |
| SDK／HTTP | 你自己寫的程式 | 自動化、儀表板、CI 整合 |

它們的能力差異只在「呈現」層——背後呼叫的是同一組 API。第四篇我們會逐一驅動它們。

## 2.3 這個設計換來了什麼

拆開 client/server 不是為了時髦，而是四個實打實的好處：

**多客戶端共用狀態。** 會話存在伺服器端的 SQLite 資料庫裡（第 5 章），任何客戶端接上來看到的都是同一份真相。不存在「哪個介面才是最新版」的問題。

**可程式化。** 核心暴露的是 HTTP API 而非終端機按鍵，代表任何語言都能驅動它。你的整合程式不需要模擬鍵盤輸入。

**遠端化。** 伺服器可以跑在算力充足的機器上，客戶端從筆電、平板甚至手機連過去。`serve` 提供的 `--hostname`／`--cors`／密碼保護全是為這個場景準備的。

**規格即文件。** 伺服器在 `/doc` 公布完整的 OpenAPI 3.1 規格，官方 SDK 直接由規格生成。API 有多少端點、吃什麼參數，不靠口耳相傳——規格就是唯一真相。

## 2.4 內嵌伺服器 vs 獨立伺服器

兩種啟動方式值得區分：

- **內嵌**：直接跑 `opencode`，TUI 啟動時順帶在隨機埠拉起伺服器。日常使用無感。
- **獨立**：跑 `opencode serve --port 4096 --hostname 0.0.0.0`，沒有介面，純粹等客戶端上門。自動化與長駐整合的正解。

官方提醒：如果已有 TUI 在跑，再執行 `serve` 會啟動**另一個**伺服器實例——兩者不共用記憶體中的狀態，但共用磁碟上的資料庫。

## 本章摘要 {.unnumbered .unlisted}

- TUI 是客戶端，伺服器才是核心——這是理解一切的起點。
- 四種客戶端（TUI/Web/IDE/SDK）共享同一份伺服器端真相。
- 收穫四項：狀態統一、可程式化、遠端化、規格化。
- `/global/health` 是你的第一個架構探針。
