# 第 20 章　發布與生態：把作品交出去

二十章的工坊之旅走到驗收臺。這一章談「交出去」的三個層次：把外掛放上生態頁讓陌生人敢裝、為你的作品許下經得起時間的相容承諾、以及回望整個系列——從按下第一次 Tab 切換代理，到今天你寫的程式正在別人的 OpenCode 裡跑。

## 20.1 生態頁：社區的正門

官方文檔的生態頁（/docs/ecosystem/）維護著社群外掛與專案清單〔文件〕。上列的方式是提交 PR——門檻不高，但清單就是信譽的初篩。上架前自問三題：

1. **裝了會壞什麼？** 你的外掛動了哪些鉤子，與熱門外掛（通知類、wakatime 類）是否搶同一個 output
2. **卸載乾淨嗎？** dispose 收得齊不齊、storage 目錄會不會留垃圾
3. **出事找誰？** README 有沒有 issue 連結與最低版本宣告

## 20.2 README 的五段式

生態外掛的 README 不是文件，是安裝決策書。實測有效的五段式：

```markdown
# opencode-<你的名字>
一句話說清楚它改變什麼。

## 為什麼需要
一個具體場景（不要功能列表）。

## 安裝
opencode.json 的 plugin 欄位片段，可直接複製。
含 options 時給最小範例與預設值表。

## 相容性
已測試的 opencode 版本區間；用了哪些 experimental 鉤子如實列出。

## 除錯
client.app.log 的 service 名稱；常見問題兩三則。
```

第三段的可複製設定片段尤其關鍵——大多數放棄發生在裝完的前三十秒。第四段的誠實是長期信譽：標了 experimental 就等於告訴使用者「上游改了我可能要跟」。

## 20.3 版本承諾怎麼下

第 12 章從消費端看過版本策略；作者端的承諾分三級：

- **保守級**：「支援 1.18.x」。只對穩定鉤子（chat.*、tool.*、event），CI 釘版測試
- **積極級**：「支援 ≥1.18」。用了新鉤子但做了特性偵測降級（第 19.4 節）
- **先鋒級**：「追 main」。experimental 重度依賴者如工作區適配器作者，README 明寫「升級前看 release notes」

無論哪級，語意化版本的紀律相同：鉤子行為改變＝major、加功能＝minor、修 bug＝patch。使用者的 @^1.2.0 能不能安心自動升級，取決於你對 patch 的潔癖。

## 20.4 從工具到資產：團隊內化

不是每個人都要發 npm。更多價值發生在組織內部：`.opencode/` 目錄進倉庫的那一刻，指令、技能、代理、主題就變成**可繼承的工程資產**。一個成熟團隊的樣貌：

```
.opencode/
├── commands/    # /deploy-check、/security-scan、/write-changelog
├── skills/      # 發布流程、事故處理手冊
├── agents/      # code-reviewer、migration-captain、docs-writer
├── plugins/     # 內網整合、審計掛鉤
└── themes/      # 品牌主題
```

新人 clone 下來的第一天，就擁有全隊十年功力濃縮的工作流。AI 時代的 onboarding，不再是「旁邊那位前輩」，而是這棵目錄樹。

## 20.5 回望：四冊一條線

第一冊你學會開引擎、下提示；第二冊你掌握模式切換、MCP 與多代理的實戰陣型；第三冊你打開引擎室，看懂 20 張表的領域模型與五條通訊通道；這一冊你從理解者變成建造者——八個擴充點、十七支鉤子、十域 API，如今都是你的零件庫。

系列的承諾從第一天就沒變過：**只寫能驗證的事**。願你帶著這套方法論離開——下一個版本號來臨時，你不會慌；遇到文檔沒寫的行為時，你知道去翻 d.ts、起一台獨立埠伺服器、用事件探針親眼看。工坊永遠為你敞開。
