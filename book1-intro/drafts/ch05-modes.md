# 第 5 章：模式切換

> **本章學習目標**
>
> - 了解 Build 與 Plan 兩種模式的本質差異
> - 學會用 Tab 鍵切換模式
> - 建立「先 Plan 後 Build」的黃金工作流
>
> **預估閱讀時間**：10 分鐘
> **實作時間**：約 10 分鐘

---

## 5.1 兩種模式的本質

OpenCode 預設有兩個主要代理，按 Tab 鍵即可切換，狀態列會顯示當前模式：

| 模式 | 能做什麼 | 不能做什麼 | 適合 |
|------|----------|-----------|------|
| **Build** | 改檔案、跑指令、執行任務 | ——（全權限） | 已經想清楚，要動手 |
| **Plan** | 讀檔案、搜尋、分析、提方案 | 改任何檔案、執行變更性指令 | 還在探索、規劃、評估 |

這個設計的巧妙之處值得說一句：Plan 模式不是靠「提醒 AI 不要改檔案」，而是直接把寫入類工具從它的可用工具清單中拿掉。工具都看不到，自然呼叫不了。權限是架構層級保證的，不是提示詞層級的希望。

> **重點**：新手最常發生的悲劇是——一進 OpenCode 就用預設的 Build 模式丟出模糊需求，代理很盡責地改了一堆檔案，結果方向完全錯。養成反射動作：**不確定時先按 Tab 切到 Plan**。

## 5.2 黃金工作流：先 Plan 後 Build

實務上最穩定的開發節奏是四步循環：

```text
1. Tab → Plan 模式
2. 描述需求，讓代理提出實作方案
3. 對方案來回討論、修正細節
4. Tab → Build 模式：「照剛才的方案執行」
```

### 實例走一遍

假設需求是「筆記軟體要支援軟刪除與回收筒」。切到 Plan 模式後輸入：

```text
使用者刪除筆記時，不要真的從資料庫移除，改成標記 deleted。
再做一個回收筒頁面，列出被刪除的筆記，可以還原或永久刪除。
請提出實作方案，包含要動到哪些檔案。
```

代理會讀完相關程式碼後回一份方案：資料庫加欄位、修改刪除邏輯、新頁面的路由與元件等等。你看完覺得「永久刪除前應該再加一次確認對話框」，就繼續在 Plan 模式補充：

```text
永久刪除前加一個確認對話框，避免誤觸。
```

方案定稿後，按 Tab 切回 Build：

```text
很好，照這份方案執行。
```

接著你會看到它依序修改檔案、建立元件、可能還主動跑起測試。全程你可以用 Esc 中斷，事後用 /undo 回退（下一章教）。

### 為什麼多一步比較快

聽起來「先討論再動手」比「直接動手」慢，實際相反：

- 在 Plan 模式修正方向的成本是「幾句對話」；在 Build 模式修正方向的成本是「改錯的檔案 + 回退 + 重來」。
- 方案文件本身就是最好的溝通紀錄，之後 commit message 或 PR 描述都能直接引用。

小任務（改文案、修一行明顯的 Bug）不必儀式化，直接 Build 也沒問題。判斷標準：**這個任務如果代理理解錯了，我收拾殘局要多久？** 超過五分鐘的，先 Plan。

## 本章摘要 {.unnumbered .unlisted}

- Build 全權限負責動工；Plan 唯讀負責偵察與規劃，權限由架構保證而非提示詞。
- Tab 一鍵切換，狀態列可確認當前模式。
- 黃金工作流：Plan 提案、來回修正、Build 執行。
- 任務風險高於五分鐘收拾成本的，一律先 Plan。
