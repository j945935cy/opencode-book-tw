# 第 18 章：Git 與 GitHub 整合

版本控制是 AI 代理的安全網（第 15、16 章已反覆出現），但 OpenCode 與 Git 生態的整合不止於此——它可以當審查員、當工單處理員、當提交訊息撰稿人。這章把 GitHub 工作流的自動化拼圖補齊。

## 18.1 PR 自動審查

**註解觸發機制**

在 GitHub 儲存庫安裝 OpenCode 的 GitHub 整合後，代理會以一個特殊成員的身分待命：在任何 PR 的討論串中輸入以 `/opencode` 開頭的留言，就能指派任務給它：

```text
/opencode 幫我審查這個 PR：
1. 檢查是否有遺漏的邊界條件
2. 確認新程式碼有對應測試
3. 標記任何與專案慣例不一致的地方
```

代理會讀取 PR 的完整 diff、相關檔案與歷史脈絡，然後直接在 PR 上回覆結構化的審查意見。

**先讓 AI 審，人再審**

推薦的審查流水線：開 PR → 自動觸發或手動叫 `/opencode` 初審 → 作者依意見修正 → 人類審查者接手最終把關。AI 初審過濾掉的是低階問題（命名、漏測試、明顯邏輯洞），人類審查者得以聚焦在架構取捨與業務正確性——兩種審查者各做各自擅長的事。

**審查提示詞的品質決定審查品質**

泛泛的「幫我看看」得到泛泛的回應。高價值的審查指令都帶具體視角：

```text
/opencode 以安全性為主軸審查這個 PR，
特別注意新增的輸入驗證是否有注入風險。
```

```text
/opencode 這個 PR 是效能優化。
請檢查 benchmark 是否真的支撐宣稱的改善，
並確認沒有犧牲可讀性換來微幅提升。
```

## 18.2 Issue 處理與提交訊息產生

**從 issue 到分支的自動化**

`opencode pr` 指令把「領工單」變成一個動作：

```bash
opencode pr 482
```

它會抓取該 PR／issue 的內容、checkout 對應分支並啟動會話，代理已經帶著完整上下文待命。搭配第 10 章的 GitHub MCP，還能做到更深的整合：「列出標了 bug 且無人認領的 issue，挑一個你能獨立修復的，先提出修復方案。」

**提交訊息產生的規範化**

每次 commit 都想半天嗎？讓代理看著 diff 寫：

```text
根據目前 staged 變更產生提交訊息。
格式：<type>: <主旨>，內文說明為什麼。
type 限 feat/fix/refactor/docs/test/chore。
```

更好的做法是把規範寫進技能（第 5 章的 commit-helper 就是現成範本），之後連提示詞都省了。

**分批提交的藝術**

一次大改動要拆成語意完整的多次提交時，代理是好幫手：

```text
目前工作區有三類混雜的變更：匯出新功能、
順手的型別修正、README 更新。
請分成三個語意獨立的 commit，逐一 staging 提交，
每個訊息符合團隊格式。
```

**紅線提醒**

- `git push` 與 `git reset --hard` 保持 ask 權限（第 3 章），永遠不嫌煩。
- AI 生成的提交訊息要快速過目——它可能把猜測寫成事實。
- 對外開源儲存庫啟用任何自動化前，先確認 token 權限範圍最小化。

## 本章摘要 {.unnumbered .unlisted}

- GitHub 整合後，PR 留言以 `/opencode` 開頭即可指派審查任務；AI 初審＋人終審的分工讓雙方都發揮所長。
- 審查指令帶具體視角（安全、效能、慣例）才有具體回報。
- `opencode pr <編號>` 一鍵領單；GitHub MCP 可再往上疊工單自動化。
- 提交訊息產生配技能規範化；混雜變更請代理分批語意提交；push 與硬重設維持 ask 是底線。
