# 第 20 章：效能優化

「效能」在代理場景有兩個維度：一是上下文的品質——會話越長，AI 越容易失焦；二是成本結構——同樣的任務用不同模型，價差可以到數十倍。這章給出上下文管理的操作學，以及一張任務×成本的選型矩陣。

## 20.1 上下文視窗管理與自動壓縮

**上下文為什麼會「變笨」**

模型的注意力是有限資源。會話累積了幾百條工具輸出之後，關鍵指令可能被大量無關內容稀釋——症狀很一致：開始重複問已經回答過的問題、忘記早先的約定、修改品質下滑。這不是玄學，是資訊密度問題。

**自動壓縮的運作**

OpenCode 的對策是自動壓縮（compaction）：當會話用量逼近上下文上限（約 95%）時，系統自動呼叫專用的 compaction 代理，把歷史提煉成摘要後重啟工作區。你在介面上會看到壓縮發生的標記，之後對話繼續，只是底層帶的是濃縮版歷史。

**主動管理勝過被動壓縮**

自動壓縮是保底而不是目標——被壓縮掉的細節就是回不來了。高手的主動做法：

1. **話題切換即換會話**。第 8 章講過的紀律，這裡補上成本視角：新會話不只是乾淨，還便宜——每個 token 都在計費。
2. **長任務先寫計畫檔**。把計畫與進度存成 Markdown（或直接放 issue），每個工作階段開場讓代理讀檔恢復脈絡。檔案是最可靠的「外部記憶」。
3. **大範圍探索走子代理**。explore 的委託機制天然隔離雜訊（第 3 章），主會話只收結論。
4. **貼 log 只貼相關段落**。「完整日誌請見 /tmp/api.log 第 200 到 260 行」優於整份傾倒。

**判斷何時該收工換新**

三個訊號：AI 開始重複犯剛剛才修正過的錯；回應速度明顯變慢；你自己在會話裡也找不到之前的結論。與其硬撐，`/sessions` 存檔、開新會話、把結論貼進去——三十秒的事，救回的是接下來半小時的產出品質。

## 20.2 模型選擇策略

OpenCode 不鎖模型，於是「什麼任務配什麼模型」變成一個值得認真回答的問題。

**任務×成本矩陣**

| 任務類型 | 特徵 | 建議檔位 |
|----------|------|----------|
| 架構設計、疑難根因分析 | 低頻、高難度、錯誤代價大 | 旗艦模型 |
| 功能實作、重構執行 | 中高頻、需要穩定編碼能力 | 中高階模型 |
| 批次改名、樣板生成、格式轉換 | 高頻、模式固定 | 輕量快速模型 |
| 會話命名、摘要等系統任務 | 海量、極簡單 | 最便宜的可用模型 |

兩個原則：

**錯誤代價決定檔位下限。** 一小時旗艦模型的費用遠低於一次生產事故。凡是「改錯要很多人收拾」的任務，不要在模型上省。

**速度也是效能。** 輕量任務用反應快的便宜模型，迭代節奏反而更順——等待本身就是成本。

**切換的操作面**

```text
TUI 內：<Tab> 相關選單即時切換目前會話的模型
CLI：   opencode run --model provider/model-name "..."
```

更省心的做法是在代理層釘模型：自訂代理可以指定自己的模型（第四冊深入），例如建立一支固定使用輕量模型的「批次處理員」，日常就沒有選擇負擔。

**用數據校準**

每月跑一次 `opencode stats`（第 11 章），看 token 分布是否符合矩陣預期。常見的偏差：旗艦模型被拿去做樣板生成（浪費），或除錯用了太弱的模型導致回合數暴增（更貴）。矩陣是起點，你的帳單才是最終裁判。

## 本章摘要 {.unnumbered .unlisted}

- 上下文過載的症狀可辨識（重複提問、忘記約定）；自動壓縮在約 95% 用量時觸發，是保底不是目標。
- 主動管理四招：話題切換即換會話、長任務外部化成計畫檔、探索走子代理、餵料只給相關段落。
- 模型選型看錯誤代價與速度需求：旗艦留給架構與疑難，批次雜活交給輕量快槍。
- `opencode stats` 定期對帳，讓矩陣跟著實際數據進化。
