# 第 11 章：會話管理

會話（session）是 OpenCode 的工作單位：一條完整的對話脈絡，連同其中的所有工具呼叫與檔案變更。新手把每件事都塞進同一個會話，高手則像指揮多條產線一樣經營多個會話。這章講兩件事：並行工作流的設計方法，以及會話的分享、匯出與遷移。

## 11.1 多會話並行工作流

**為什麼要拆會話**

三個理由：上下文隔離（不同任務的雜訊互不汙染）、可恢復性（某條線走偏了直接捨棄，不傷及其他進度）、可並行（等 A 任務跑測試時推進 B 任務）。

**基本操作**

```text
<Tab>            開新會話
/sessions        列出歷史會話並切換
opencode --continue   CLI 直接續上最近一次會話
```

CLI 端還能指定續哪一個、甚至分岔：

```bash
opencode session list
opencode run --session ses_xxx "繼續剛才的重構，處理剩下的檔案"
opencode run --fork --session ses_xxx "換個方向：改用策略模式重做"
```

`--fork` 的價值在「平行宇宙」：從同一個時間點分出兩條嘗試路徑，各跑各的，最後擇優保留。

**命名是紀律的一部分**

預設會話名稱是自動生成的時間戳，三天後你自己都認不得。養成習慣：開新會話先 `/sessions` 改個有意義的名字，或用 `--title` 直接指定：

```bash
opencode run --title "修購物車折抵Bug" "..."
```

一週後回顧工作軌跡時，你會感謝這個習慣。

**並行的實務節奏**

單機同時開三四個終端分頁、各掛一個會話是完全可行的。但注意兩條底線：

1. **同一個工作目錄別讓兩個代理同時寫碼。** 檔案衝突沒人替你調解。正確做法是 git worktree（或直接 clone 第二份）讓每個會話有自己的目錄。
2. **並行的是等待期。** A 會話在跑長測試時切到 B 推進——並行提升的是時間利用率；若四個會話都在等你下決策，那不是並行，是多工混亂。

## 11.2 會話分享與協作

**/share：把對話變成網頁**

TUI 輸入 `/share`，OpenCode 把整個會話（含你的問題、AI 的推理、工具呼叫、diff）發布成一個可分享的網址，任何人打開就能像看逐字稿一樣檢視整個過程。

典型用途：

- **請求協助**：貼網址給同事或社群，「第三步它為什麼選了方案 B？」比口述快十倍。
- **留下決策紀錄**：PR 描述裡附上關鍵會話連結，審查者能看到實作過程的完整推理。
- **教學示範**：把標準工作流錄成一份可分享的活教材。

敏感專案的防護見第 19 章——可以全域停用分享功能。

**export／import：帶著會話走**

```bash
opencode export ses_xxx > bug-analysis.json
opencode import bug-analysis.json
```

匯出的是 JSON 格式的完整事件序列（第 2 章講過的一切皆事件）。用途包括：跨機器搬運工作現場、把除錯過程存進知識庫、離線分析代理的行為模式。

**stats：看清成本**

```bash
opencode stats
```

列出 token 用量與費用統計。長期使用者建議每月看一眼：哪類任務燒最多 token？有沒有該換便宜模型的場景？第 20 章的成本矩陣會接著這個話題。

## 本章摘要 {.unnumbered .unlisted}

- 拆會話的三個收益：上下文隔離、可恢復、可並行；`--fork` 能從同一節點分岔出平行嘗試。
- 會話命名是未來的自己給現在的自己最好的禮物；`--title` 與 `/sessions` 是基本配備。
- 並行鐵律：一個目錄一個寫手，要多寫手就 worktree 分身。
- `/share` 生成可分享網頁，適合求援、留紀錄、做教材；`export/import` 讓會話變成可攜資產；`stats` 定期看成本。
